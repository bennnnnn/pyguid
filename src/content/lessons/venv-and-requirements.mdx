## Why this matters

Without virtual environments, global pip installs break other projects and tutorials. requirements.txt documents what your app needs so teammates and deploys match your machine. This is standard practice before installing third-party libraries for data science, automation, or larger projects.

Your project gets its own **sandbox** so package versions do not fight other projects. A **virtual environment (`venv`)** is that sandbox; **`requirements.txt`** lists what to install.

## One new idea: venv per project

On your computer (terminal):

```bash
python -m venv .venv
source .venv/bin/activate   # Mac/Linux
# .venv\Scripts\activate    # Windows
pip install requests
pip freeze > requirements.txt
```

| Step               | Why                            |
| ------------------ | ------------------------------ |
| `python -m venv`   | create isolated Python         |
| `activate`         | use that Python for `pip`      |
| `requirements.txt` | share exact packages with team |

## requirements.txt example

```text
requests==2.31.0
```

Teammates run:

```bash
pip install -r requirements.txt
```

<Callout variant="note">
  PyGuide lessons do not run `pip` in the browser. Learn the commands locally when you
  start real projects.
</Callout>

## Recap

- **`venv`** — isolated environment per project
- **`pip freeze > requirements.txt`** — save dependencies
- **`pip install -r requirements.txt`** — restore them
