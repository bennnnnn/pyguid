## Why this matters

Tracebacks look long on purpose—they carry breadcrumbs. Readers who skim **bottom-up** locate the actionable sentence first; skipping that habit wastes minutes per bug.

## What a SyntaxError traceback tells you

<PythonExample filename="read_syntax_demo.py" code={`print("Oops"`} />

Expect output shaped roughly like:

```text
  File "... line 1
    print("Oops"
         ^
SyntaxError: ...
```

1. **`SyntaxError`** class — grammar problem
2. **Line number** — where parsing failed (often nearby the real omission)
3. **`^`** caret — where Python realized things broke

## NameError is shorter but same bottom-first rule

<PythonExample filename="read_name_error.py" code={`print(unknown_person)`} />

Final line mentions **NameError** and **`unknown_person`** — that pair is your search target.

Define it—or fix typo—and rerun:

<PythonExample filename="read_name_fixed.py" code={`unknown_person = "Taylor"
print(unknown_person)`} />

## Recap

- Read the **bottom line first** → **error family** (`SyntaxError`, `NameError`, …)
- Climb upward for **filename + line number** plus caret context
- Change **one** likely issue, rerun—iterate instead of rewriting everything
